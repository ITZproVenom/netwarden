# NetWarden for iPhone

A native SwiftUI app that brings the parts of NetWarden that actually work on
iPhone. iOS apps run sandboxed with no raw-packet or privileged-low-level
network access, so the desktop capture pipeline (ARP/NDP discovery, gateway
security, disconnect controls, bandwidth limits, traffic monitoring) cannot
run on iPhone. This app is deliberately a companion, not a port.

## What works on iPhone

- **Current network identity** — this iPhone's IPv4/IPv6 addresses per
  interface (from the sandbox-safe `getifaddrs` API) and, where the system
  grants it, the connected Wi-Fi network name.
- **mDNS discovery** — browses service types (`_http._tcp`, `_airplay._tcp`,
  `_ssh._tcp`, `_printer._tcp`, …) using Apple's Network framework and shows
  what those devices advertise. This is the only real on-device discovery an
  iOS app can perform: it does not enumerate every device on the network, only
  devices that advertise services.
- **Device registry** — a native Devices view backed by a bundled sample scan
  snapshot plus an importer for snapshots exported from the NetWarden desktop
  app. Import a JSON snapshot, search it, open devices, and assign nicknames.

Everything else — live network scans, gateway-security alerts, temporary
disconnects, bandwidth limits, per-device traffic monitoring — requires the
privileged helper and raw packet access that exist only in the desktop app.

### iOS limitations in detail

iPhone apps cannot open raw sockets or read/forge ARP or ICMPv6 packets, so:

- ARP/NDP device discovery and IPv6 state tracking: not possible.
- Router/gateway identity monitoring: not possible.
- ARP/NDP redirection used for disconnect and bandwidth control: not possible
  and would violate App Store rules even with a personal-VPN entitlement.
- Traffic shaping: not possible.

## Requirements

- macOS with Xcode 26 or newer (the iOS 26 SDK ships the Liquid Glass
  SwiftUI APIs used by the UI). Deployment target is iOS 17, with Liquid Glass
  applied only on iOS 26+ and a plain material fallback on older systems.
- The project is defined in `project.yml` (XcodeGen). `brew install xcodegen`
  regenerates `NetWarden.xcodeproj`. The committed `.xcodeproj` is checked in
  for direct use and is regenerated by CI every build.

## Build

```sh
brew install xcodegen
cd ios
xcodegen generate --spec project.yml
xcodebuild -project NetWarden.xcodeproj \
  -scheme NetWarden -configuration Release \
  -sdk iphoneos -destination 'generic/platform=iOS' \
  -derivedDataPath build/DerivedData build
```

The GitHub Actions workflow `.github/workflows/ios.yml` runs the build on the
`macos-26` runner and packages the resulting unsigned IPA.

## Signing

The CI workflow builds with `CODE_SIGNING_ALLOWED=NO` and produces an
unsigned `.ipa` (the `.app` packaged into `Payload/`). No certificates or
provisioning profiles are invented or stored.

To install an unsigned IPA on a device, sign it at install time with a
sideloading tool (AltStore, SideStore, Sideloadly, Apple Configurator) using
your Apple ID, or sign it with your own certificate/profile. If you use the
optional Access-WiFi-Information entitlement (below), the signing identity
must carry that capability.

The app carries no entitlements that must be present for the app to launch.

### Optional Access WiFi Information entitlement

`NetWarden.entitlements` declares `com.apple.developer.networking.wifi-info`,
which lets the app read the current network's SSID via
`NEHotspotNetwork.fetchCurrent` with the user's location permission. This is
best-effort: it has no effect when the app is sideloaded unsigned, and the
Network view simply omits the network name then. With a paid developer account
you can enable **Signing & Capabilities → Access WiFi Information** instead.

The mDNS Discover tab uses the standard iOS Local Network permission
(`NSLocalNetworkUsageDescription`) and requires no entitlement.
